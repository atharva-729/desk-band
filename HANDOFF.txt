0. TL;DR
--------
Desk Band turns any table into a musical instrument, using only the phone already in your pocket.
Lay the phone flat on the table and knock nearby spots. The phone's MICROPHONE (spectral "fingerprint" of the knock)
and MOTION SENSOR (direction of the jolt) work out WHICH spot was hit and HOW HARD. A tiny logistic-regression
model, trained in the browser from about 60 knocks, sends {zone, confidence, velocity} to the laptop. The laptop plays
drums, desi percussion, marimba, a melody kit, chords, or user-editable chords, or sends MIDI out.

No extra hardware, no app install, no AI/LLM, no cloud. Phone = a web page. Laptop = Python stdlib server + a web page.

Status: WORKING ON A REAL iPHONE 17 (Atharva played it, Nov 2026, and was very happy: "works so much better").
The demo build (QR join, training saved on the laptop, "How it hears" explainer panel, camera card, record button)
is browser-tested but NOT yet used live in a meeting.

4. EXPERIMENT RESULTS (offline, from his recordings)
---------------------------------------------------
Raw audio is NOT in the repo (personal recordings). Derived features from run 3 ARE:
data/sessions/run3_features.npz with
  FA = 120 x 19 audio features, FC = 120 x 34 accel features (first 7 = the compact set the browser uses),
  y = spot label, p = pass (1 or 2).

Run 1, phyphox "Acceleration (without g)" only, 100 Hz, 4 spots x about 10 taps, done in blocks:
  - Leave-one-out about 70% vs 25% chance.
  - CAVEAT: taps were done in blocks, so time drift could be helping the model.

Run 2: unusable. The labels couldn't be recovered (no clean groups, a random section at the end).
  Lesson: never rely on the user's memory for labels → guided prompting.

Run 3, the main evidence. Phyphox accel at 100 Hz plus an iPhone Voice Memo (still 16 kHz AAC: the Lossless setting
was off):
  - One loud thump to sync, then 8 groups x 15 taps in the order 3,1,4,2 | 2,4,1,3.
  - The audio started about 16.31 s before the accel recording (found by matching events).
  - Train on pass 1, test on pass 2, and vice versa (separately recorded, different order). Logistic regression:

        accelerometer only  66%
        microphone only     76%
        both combined       82%   (chance 25%)

  - Same pipeline written in JS (static/core.js), run in Node over that recording, 10–15 training taps per zone: 79–88%.
  - Detection gotcha found: the old fixed absMin threshold of 0.003 missed most taps at the quiet spot 3. Fixed by
    absMin 0.0005 plus an adaptive noise floor x thrMult (default 5).

Speed vs accuracy (listening window after the knock peak, run 3, both pass directions averaged roughly):

        Fast      30 ms window   ~45 ms phone listening delay   ~71%
        Balanced  45 ms window   ~61 ms                          ~77%   <- default
        Accurate  70 ms window   ~84 ms                          ~80%

Simple browser classifiers compared on run 3 (8 taps/zone): nearest-centroid ~70%, 3-NN ~65%,
plain logistic regression ~78%. So: logistic regression, hand-written in core.js.


5. LIVE FEEDBACK FROM ATHARVA AND WHAT WAS DONE
-----------------------------------------------
v0 feedback:
  (a) "some latency, but not much";
  (b) he had to wait about 0.5 s between notes, so no melodies;
  (c) "a lot of my taps went to number one";
  (d) no chords.
Fixes in v0.2:
  (b) Root cause was my code: a 200 ms refractory, plus no new onset while one was pending (~100 ms), plus a 250 ms
      anti-echo mute. Now: overlapping pending onsets, 90 ms refractory, a rising-edge check (m > 1.8 x previous frame)
      so ringing tails don't retrigger, anti-echo OFF by default (150 ms when on). The offline test catches 20/20
      knocks at 8 per second.
  (a) ScriptProcessor buffer 1024 → 256; 45 ms listening window by default; Response setting; the stage shows the
      phone's measured listening delay (~56 ms in a browser test).
  (c) Probably caused by block-wise training. Now GUIDED TRAINING: random-order prompts, 15 per zone, "mix soft and
      hard knocks". Plus FIX-IT-WHILE-PLAYING: tap the right pad on the phone after a wrong note → that knock is
      added with the right label and the model retrains.
  (d) Two simultaneous knocks can't be separated with one phone (one blended event). Added a Chords kit
      (C/G/Am/F strums), MIDI out (Chrome/Edge → GarageBand/Ableton via IAC or loopMIDI), and later a "My chords"
      EDITOR (type note names per pad, e.g. "A3 C4 E4"; pluck/keys; ringing/stab; strummed/all-at-once; saved in
      browser localStorage). A "teach 1+3 together as an extra class" combo idea is in README Phase 1 as a go/no-go.
After v0.2: "Dude it works so much better… this is very very good now."
Melody kit (C D E G) was added for Mary Had a Little Lamb and Hot Cross Buns. Twinkle Twinkle needs 6 notes,
so it's waiting for the 6–8 pad version.

6. ARCHITECTURE / FILE MAP
--------------------------
server.py
  - Python 3.9+ stdlib (optional `cryptography`, otherwise the `openssl` CLI, for the self-signed cert).
  - Phone:  https://<lan-ip>:8443. HTTPS is REQUIRED for the mic + DeviceMotion on iOS. PhoneServer peeks the first
    byte: TLS → serve; plain HTTP → 301 to https. That fixed his ERR_CONNECTION_CLOSED when Chrome iOS opened http://.
  - Laptop: http://localhost:8000 (stage).
  - Routes: / (phone or stage by port), /phone.html, /stage.html, /core.js, /vendor/qrcode.js,
    /events (SSE; sends hello plus a replay of last_ready), POST /hit (relay to all SSE subscribers),
    GET/POST /samples?resp=NN, GET /info → {phone_url}.
  - The cert is cached in .certs/cert-<ip>.pem (gitignored); it's regenerated if the IP changes, so the phone shows the
    warning again.

static/core.js  (shared by the phone page and the Node tests; NO dependencies; works as UMD/CommonJS)
  - fft():             radix-2 in place.
  - audioFeatures(seg, sr): Hann window → 4096 FFT → 18 log-spaced bands 150–7900 Hz → log energy, minus the mean
                       (shape), plus the mean (level) = 19 values.
  - accelFeatures(samples, tPeak, beforeMs=40, afterMs): per-axis RMS normalised (3) + signed peak per axis
                       normalised (3) + log norm (1) = 7. Returns zeros if no motion data (mic-only still works).
  - Detector:          one-pole high-pass ~150 Hz → 64-sample frames → adaptive noise floor (EMA when below
                       threshold) → onset if frame max > max(noise*thrMult, absMin) AND rising AND past the
                       refractory AND not muted → pending list → after search(12 ms)+post(window) samples, find the
                       peak, cut [-5 ms, +post] → onHit({peakIdx, peakAmp, seg, wallMs, thr, delayMs}).
                       muteUntilMs is used for screen touches (700 ms) and anti-echo.
  - Model:             multinomial logistic regression, z-scored features, gradient descent
                       (iters 600, lr 0.2, l2 0.05). predict → {zone, prob, probs}.

static/phone.html
  - Start sensors: DeviceMotionEvent.requestPermission on iOS (needs a user gesture); getUserMedia with
    echoCancellation, noiseSuppression and autoGainControl all FALSE; ScriptProcessor 256; wake lock.
  - Settings:
      * Sensitivity (thrMult 3–12, default 5).
      * Response (30/45/70 ms). Training data is stored PER Response setting: localStorage key deskband.v2.<ms>
        plus the server copy.
      * Anti-echo checkbox.
  - Modes: idle | guided (random queue, 15/zone) | topup (tap a pad → +8 taps there) | play.
  - In play, it POSTs {type:"hit", zone, prob, vel, delay, probs, fp(18), wave(60)}. Play sends
    {type:"ready", fingerprints, taps, acc}.
  - The accuracy estimate is 4-fold CV on the training taps (optimistic: same-session).
  - Export taps → JSON download.

static/stage.html
  - Kits: drums, desi, marimba, chords, melody (C D E G), custom ("My chords" editor). All sounds are synthesised in
    WebAudio; no sample files.
  - MIDI out map per kit (drums on ch 10, GM notes 36/38/42/39).
  - Keys 1–4 trigger pads (useful for testing without the phone).
  - Explainer, timeline, QR join card, camera, recorder (see Section 5).

tests/test_core.js        Offline synthetic test (detection + classification + rapid-fire 8/s). Run: node tests/test_core.js
tools/analysis/*.py       The Python scripts used on the phyphox/Voice-Memo recordings (tap detection, alignment,
                          segmentation, cross-pass scoring, classifier comparison, plots). They take file paths as
                          arguments; segment.py/score.py have run-3-specific window times and OFF=16.31 hard-coded.
tools/analysis/test_core_on_recording.js
                          Runs core.js over a recording:
                          node … <core.js> <audio.f32 raw mono float32 16k> <accel.csv> <postMs> <accAfterMs> <dropLevel 0/1>
tools/browser-tests/e2e_demo.js
                          Playwright: feeds a WAV as a FAKE MIC (Chromium flags --use-fake-device-for-media-stream
                          --use-file-for-fake-audio-capture=<wav>), runs guided training, checks the laptop-saved
                          training loads on a fresh phone, plays, checks the explainer, records a demo.
                          Run the server first. The accuracy it prints is meaningless (prompts are random vs the fake
                          audio); it checks plumbing.
tools/browser-tests/chord_editor.js
                          Playwright check of the chord editor (parsing, errors, persistence).
data/sessions/            Exported tap features. NEVER raw room audio.
data/training/            Laptop copy of training taps (gitignored).
README.md                 Phased plan with checkpoints (Phase 0 done, Phase 1 next), demo instructions,
                          phyphox backlog.


7. KNOWN ISSUES / GOTCHAS
-------------------------
- The self-signed cert warning appears on the phone each time the cert is new. A plain-http visit is now redirected.
  Office/guest Wi-Fi may block phone↔laptop traffic; fall back to the phone hotspot.
- ScriptProcessorNode is deprecated. Move to an AudioWorklet in Phase 1 (also lower latency).
- Safari DeviceMotion is about 60 Hz (phyphox gave 100 Hz). Motion is the weaker feature anyway.
- One phone can't separate two simultaneous knocks (a blended event). Chords = one pad strums a chord.
- The estimated accuracy shown on the phone is same-session CV, so it's optimistic. Report real numbers only from
  separately recorded, prompted sessions.
- If the laptop speakers are on the same table, the phone hears the drum → possible re-trigger. Use headphones, or
  the anti-echo toggle.
- ZONES is hard-coded to 4 in BOTH phone.html and stage.html (ids 1–4, colours, grid order 1 2 / 4 3), and the chord
  editor / KITS / MIDI_MAP assume 4. Generalising to N pads is the next real task.
- Webcam card may not open on Windows while Teams/Meet holds the camera.
- Recording is .webm (plays in Chrome/VLC; QuickTime won't). Convert with ffmpeg if needed.
- Not yet tested: Android, a different table, moved phone, next-day reuse, more than 4 pads.

9. PHYPHOX EXPERIMENT BACKLOG (he loves this; each is a quick test first)
-------------------------------------------------------------------------
Phyphox remote access lets Python on the laptop read live sensor buffers over HTTP
(see https://phyphox.org/docs/remote-interface/ ; GET /get?<buffer>=… and /control?cmd=start|stop|clear).
  1.  Barometer room events: door close / AC on → pressure blips.
  2.  Barometer stair counter / building height.
  3.  Appliance stethoscope: accel spectrum on a fridge, washing machine or desk near a fan → identify the appliance.
  4.  Ball bounce lab: acoustic stopwatch → coefficient of restitution; cricket vs tennis vs ping-pong ball (sports!).
  5.  Air theremin via the iPhone depth sensor → laptop synth.
  6.  Sonar ruler (speaker + mic echo).
  7.  Doppler speedometer.
  8.  Spin challenge (gyro RPM).
  9.  Magnet ring controller (magnetometer). MagSafe accessories contain magnets. Raw magnetometer isn't available to
      plain web pages (Android Chrome needs a flag; iOS Safari only gives a heading), so use phyphox.
  10. Heartbeat on the chest via accel. Just for fun; explicitly NOT a medical tool.
Earlier context on why the magnet is needed: an accelerometer only senses the phone's OWN motion, so a still phone
can't feel a hand moving near it. A magnet field (magnetometer), light, radio or sound must carry the signal.
Samsung's Air Gesture used a special IR sensor, and S Pen Air Actions put the IMU in the pen (dropped on the S25 Ultra).


10. PRIOR ART TO CITE (not repeat)
----------------------------------
- Mogees (2014): any surface as an instrument, but needs a separate contact sensor plugged into the phone.
- Vibrative (Florian Kräutli, 2012): typing on a table via a jailbroken iPhone 4 accelerometer, ~80%.
- Around-device magnet input research (2010s; ring-twist 2019; text entry 2021). Google Cardboard magnet button.
- Elliptic Labs: ultrasound gestures built into phones.
Our angle: zero accessories, mic + motion fused, a plain web page, aimed at any phone, all on-device.


11. TALKING POINTS ALREADY GIVEN TO HIM (for the Anand meeting)
--------------------------------------------------------------
1. The hook: a table becomes a drum kit with only the phone in his pocket; no sensors, no app, just a web page.
2. How it works: every spot rings differently (sound fingerprint) plus jolt direction; a tiny model learns ~60 knocks
   in a minute.

   8+ notes/s.

   button accessibility input.
6. Honest limits and next steps: training per setup, lag noticeable to real drummers, Android untested; 6–8 pads,
   robustness, a link anyone can try.
